# Использование AI

Проект разрабатывался с применением AI-инструментов. Они использовались для
ускорения рутинной реализации, анализа контракта, подготовки черновиков и
дополнительного ревью. Требования, архитектурные границы, проверка результата и
ответственность за итоговый код оставались на стороне кандидата.

## Как использовался AI

AI помогал:

- готовить черновую реализацию по детальным техническим заданиям;
- настраивать Vite, TypeScript, ESLint, Vitest, React Testing Library, TanStack
  Query и MSW;
- анализировать OpenAPI-схему и подготавливать generated-контракт и
  HTTP-клиент;
- переносить правила дизайн-документа в локальные токены и UI-примитивы;
- реализовывать отдельные вертикальные срезы после определения их контрактных и
  архитектурных ограничений;
- запускать автоматические проверки, искать проблемы в конфигурации и
  актуализировать документацию.

AI не использовался как самостоятельный источник продуктовых требований.
Предложения проверялись по ТЗ, OpenAPI, макетам и фактическому поведению
приложения. Решения, противоречившие этим источникам или усложнявшие проект без
необходимости, отклонялись либо перерабатывались.

## Ответственность кандидата

Кандидат:

- определил основной пользовательский сценарий и разделил работу на
  последовательные этапы;
- выбрал архитектурные границы и направление зависимостей;
- закрепил TanStack Query владельцем серверного состояния и не допустил его
  дублирования в глобальном store;
- отделил MSW от production-кода, чтобы mock backend можно было заменить
  реальным API без перестройки UI;
- определил OpenAPI как единственный источник DTO и отказался усиливать
  optional-поля предположениями;
- задал модель транспортных ошибок с разделением HTTP, network, abort и parse
  errors;
- определил границы generated API, presenter/ViewModel и UI-композиций;
- выбрал Base UI и локальные SCSS Modules вместо CSS-фреймворка;
- проверял реализацию по коду, тестам и в браузере, находил несоответствия и
  корректировал решения;
- отвечает за итоговый код и может объяснить принятые решения и ограничения.

## Ключевые решения

### Поэтапная реализация

Проект развивался вертикальными срезами: технический фундамент, API-граница,
UI kit, список аукционов, фильтры, детали, история и установка ставки.

Такой порядок позволил не создавать DTO, доменные модели, stateful-моки и
продуктовые абстракции до появления конкретного сценария. На каждом этапе
добавлялись только необходимые модули и проверки.

### Слоистая архитектура

Используется облегчённая архитектура, вдохновлённая Feature-Sliced Design:

```text
app → pages → features → entities → shared
```

Директории и публичные API создаются по фактической потребности. Пустые слои,
декоративные barrel-файлы и абстракции «на будущее» не добавляются.

### Владение состоянием

За удалённые данные отвечает TanStack Query. Данные аукционов не копируются в
Zustand, MobX или локальное хранилище приложения.

React Hook Form владеет редактируемым состоянием форм, URL — применёнными
фильтрами, TanStack Router — маршрутами и route params. Благодаря этому у
каждого вида состояния остаётся один понятный владелец.

### Заменяемый mock backend

MSW используется как тестовая реализация Auction API. Product-код не импортирует
handlers, fixtures или внутреннее состояние моков.

Stateful-поведение MSW нужно для проверки установки ставки и согласованности
последующих GET-запросов. Оно не выдаётся за production-аукционный движок и не
определяет недокументированные правила реального backend.

### Контрактная граница API

OpenAPI является источником DTO и операций. Generated-код изолирован внутри
API-слоя и воспроизводится скриптом. Рукописный транспорт отвечает за
runtime-конфигурацию и обработку ошибок, но не копирует generated schemas.

Во время аудита были зафиксированы ограничения контракта:

- большинство вложенных schemas не содержит `required`;
- успешный ответ установки ставки не имеет response body;
- не описаны idempotency key, revision и отдельный конфликт `409`;
- отсутствует надёжный идентификатор собственной ставки в истории;
- правила min/max/step и переходы некоторых статусов определены не полностью;
- Bearer security объявлена без источника токена в рамках тестового приложения.

Эти пробелы не заполнялись изменениями generated-типов или скрытыми
предположениями в production-коде. Неоднозначные правила остаются
ответственностью backend-контракта.

### UI kit и стили

Глобально оставлены только дизайн-токены, reset и базовые правила. Layout-стили
и стили компонентов находятся рядом с владельцами в SCSS Modules.

UI kit построен на Base UI и содержит только переиспользуемые примитивы: кнопки,
поля, select/combobox, number field, switch, tabs, статусы, dialog, tooltip,
pagination, skeleton и состояния данных. Product-композиции, включая карточку
аукциона и форму ставки, не помещаются в `shared/ui`.

При визуальном ревью были исправлены, среди прочего, центрирование стрелок
select/combobox, активное состояние навигации, мобильные отступы и состояния
интерактивных элементов. Изменения вносились в компоненты-владельцы, а не
маскировались глобальными стилями.

### Список, фильтры и URL-state

Список реализован как контрактный вертикальный срез: query options, presenter,
карточка, MSW handler и наблюдаемые состояния страницы.

Фильтры разделены следующим образом:

- React Hook Form хранит draft;
- URL хранит применённые значения;
- mapper переводит URL-модель в `AuctionListRequest`;
- TanStack Query включает request в query key;
- MSW применяет фильтрацию до пагинации.

Реализован ограниченный набор полей, подтверждённый контрактом и mock-данными.
Формальный перенос всех полей `AuctionListRequest` был отклонён, поскольку
создал бы ложную полноту.

Проверялись прямое открытие URL, reload, Back/Forward, сброс страницы при
изменении фильтров, отсутствие запроса до Apply, невалидные optional-параметры и
empty state от реальной фильтрации.

### Детальная страница

Детали загружаются через `GET /auctions/{auctionUuid}` и не используют list DTO.
Optional-поля не заменяются выдуманными значениями. Разделены `404`, системная
ошибка и retry; возврат через browser history восстанавливает URL-state списка,
не перенося фильтры в detail URL.

В ходе проверки были согласованы route points, вес, объём, расстояние, временной
график, цена за километр и доступность действия. Layout проверен при 1280×720 и
390×844 без горизонтального overflow.

### История ставок

История использует отдельный endpoint и независимый query key с UUID аукциона.
Её loading, error, empty и retry локализованы внутри секции и не блокируют
детали.

UI сохраняет серверный порядок. Колонка статуса появляется только при наличии
контрактных значений `is_win`, `is_counter` или `is_rejected`. Стартовая цена не
изображается ставкой участника.

В текущем контракте нет идентификатора собственной ставки. В mock-сценариях
собственная строка сопоставляется с `last_bet` и получает текстовый маркер
«· Вы». Это локальное демонстрационное ограничение, а не универсальное
бизнес-правило: при равных суммах для достоверной персонализации backend должен
вернуть owner-id либо явный признак принадлежности.

### Установка ставки

Сценарий реализован через generated `setBet`, React Hook Form, Zod и TanStack
Query mutation. Форма доступна только в разрешённом сервером состоянии.

После успешной операции инвалидируются связанные queries деталей, истории и
списка. UI не вычисляет подтверждённое серверное состояние из отправленного
payload и не использует optimistic update.

Обработаны:

- клиентская валидация;
- блокировка повторной отправки кликом и Enter;
- success только после ответа сервера;
- `422` без ложного success, с сохранением введённого значения и обновлением
  данных;
- системная ошибка с возможностью повторной отправки;
- сброс изменяемого MSW-состояния между тестами;
- отсутствие формы для завершённого аукциона.

Отдельный сценарий конфликта с `409` не имитируется, поскольку OpenAPI не
описывает revision или conflict protocol. Клиент обрабатывает только
подтверждённые контрактом ответы.

### Fixed-price

Для fixed-price пользователь принимает заданную цену без редактирования суммы.
Используется общий generated endpoint установки ставки, поскольку отдельной
операции принятия цены в OpenAPI нет.

После принятия mock backend обновляет детали, список и историю. Конкретный
переход статусов реализован только для согласованного тестового сценария и
должен быть подтверждён владельцем реального backend-контракта.

### Архитектурный рефакторинг

После отдельного ревью были закрыты несколько реальных протечек
ответственности:

- detail-страница переведена на подготовленную bid ViewModel;
- mutation orchestration вынесена из формы;
- draft-валидация фильтров сосредоточена в Zod-схеме;
- безопасное чтение `trace_id` перенесено в `shared/api`;
- временный справочник городов отвязан от конкретного UI-компонента.

Repositories, use-case classes, универсальные mutation factories и
дополнительные domain models не создавались: для текущего объёма они увеличили
бы сложность без прикладной пользы.

### Уровни тестирования

Тесты разделены по фактической границе:

- unit — чистые функции и правила;
- scenario — пользовательские сценарии с React Testing Library, memory router,
  TanStack Query и MSW;
- e2e — зарезервирован для реальных браузерных сценариев; фиктивный runner не
  добавлялся.

Generated API, внутренности TanStack Query, Router и MSW отдельно не
тестируются. Проверяется наблюдаемое поведение приложения и воспроизводимость
генерации.

## Изменённые или отклонённые предложения

В ходе разработки были отклонены или ограничены:

- пустые слои, barrel-файлы и абстракции «на будущее»;
- глобальный store без сценария глобального клиентского состояния;
- ручное дублирование OpenAPI DTO и runtime-клиент без необходимости;
- Axios и CSS-фреймворк;
- изменение generated-файлов вручную;
- неподтверждённые правила min/max/step, auth flow и определение победителя;
- optimistic update, polling, WebSocket и локальная event-sourcing модель;
- полный набор из 44 фильтров без данных и определённого mapping;
- React Router после обнаружения прямого несоответствия обязательному стеку;
- искусственный сценарий stale bid с `409`, отсутствующий в OpenAPI;
- автоматический `audit fix --force` без анализа breaking changes.

## Проверка результата

Реализация проверяется с помощью:

- форматирования, ESLint и TypeScript typecheck;
- Vitest и React Testing Library;
- production-сборки;
- повторной генерации OpenAPI-кода и проверки воспроизводимости;
- сценариев списка, фильтров, деталей, истории и установки ставки;
- проверок loading, empty, error/retry, `404`, nullable-полей и маршрутизации;
- проверки защиты от двойного submit и отсутствия ложного success;
- визуальной проверки desktop и mobile, включая отсутствие горизонтального
  overflow;
- итогового просмотра Git diff на предмет случайных файлов и несвязанных
  изменений.

AI помогал запускать проверки и анализировать результаты. Кандидат воспроизводил
ключевые сценарии, проверял реализацию и отвечает за интерпретацию результатов.

## Текущие ограничения и риски

В реализацию намеренно не входят:

- runtime-validation всех response DTO;
- Bearer token flow и production API integration;
- полноценные доменные модели аукционов;
- серверная пагинация истории;
- достоверное определение собственной ставки без серверного идентификатора;
- подтверждённые backend-правила шага ставки и idempotency/revision token;
- production-аукционный движок;
- realtime-таймер, polling и WebSocket;
- неподтверждённые фильтры и произвольная сортировка;
- deployment и CI/CD.

Остаются задачи дополнительной проверки:

- Safari и Firefox;
- автоматизированный accessibility-аудит и полный keyboard-flow сложных
  контролов;
- проверка dependency advisories в среде с доступом к registry;
- responsive dialog или сворачиваемая панель для длинной мобильной формы
  фильтров.

  одинаковых ставок, fixed-price и переходов статусов;
- сильнее проработал бы дизайн, адаптивные состояния и визуальную иерархию
  ключевых сценариев;

  компромиссы;
- провёл бы кроссбраузерную проверку в Safari и Firefox;
- добавил бы accessibility-аудит ключевых сценариев и keyboard-flow Base
  UI-компонентов;
- проверил бы advisories зависимостей и точечно обновил затронутые пакеты;
- добавил бы первые браузерные E2E для критического пути списка, деталей и
  установки ставки;
- улучшил бы мобильное представление расширенных фильтров после подтверждения
  продуктового приоритета.

## Итог

AI ускорил рутинную реализацию, анализ схемы, настройку инструментов и поиск
проблем. Кандидат определил требования и архитектурные границы, проверял

за итоговый результат.

Рабочий процесс:

```text
требования → архитектурные границы → реализация → ревью → корректировка → проверка
```
